# Designing and developing Flint, an AI agent harness with Ollama and OpenAI

## Context

The use of artificial intelligence agents relies on mechanisms often obscured by orchestration frameworks and platforms.

Behind a conversational interface, an agent must manage several operations: transmit context to a model, interpret its tool usage requests, execute these tools, retrieve their results, and continue reasoning until producing a response.

To understand and control these mechanisms, I undertook to develop **FLINT**, my own *agent harness*, with the assistance of OpenAI Codex.

The project is based on an architecture allowing the use of local models with **Ollama** as well as models accessible via the **OpenAI API**.

My goal was to build an experimentation environment in which the agent's execution loop remains explicit, understandable, and modifiable.

## Objectives

- Deeply understand how an AI agent works.
- Develop an orchestration loop independent of a complete agentic framework.
- Connect local models via Ollama and remote models via the OpenAI API.
- Standardize interactions with different model providers.
- Frame iterations and stopping conditions.
- Explore local persistence and MCP tools integration.
- Use Codex to accelerate development and deepen my understanding of the architecture.

## Approach and implementation

### 1. Designing an explicit agent architecture

I structured Flint around the main responsibilities of an agentic execution environment:

- A client responsible for communicating with the model.
- An orchestration loop.
- A registry of available tools.
- An execution mechanism for tool calls.
- A history of messages and observations.
- Continuation and stopping conditions.

This separation allows understanding the role of each component and evolving the architecture progressively.

### 2. Integrating Ollama and the OpenAI API

I developed Flint to explore two modes of access to language models.

**Ollama** allows using models executed locally.

**The OpenAI API** allows interacting with models hosted remotely.

The project provides adapters behind a common interface, to limit the orchestrator's dependency on a particular provider.

This approach facilitates experimentation and comparison of different model configurations.

### 3. Implement the agent execution loop

The core of Flint relies on a loop that organizes exchanges between the model and its environment.

At each iteration:

1. The conversational context and available tools are passed to the model.
2. The model produces a response or requests the execution of a tool.
3. Flint interprets any tool calls.
4. The requested tools are executed.
5. Their results are added to the context as observations.
6. The model is solicited again to continue processing.

When no tool call is requested and a final response is available, the agent ends its turn.

**This explicit loop constitutes the technical core of the project.**

It allows precise observation of how a language model transitions from text generation to tool usage.

### 4. Build a registry and a mechanism for executing tools

Flint uses a registry to expose the tools accessible to the model.

The model receives their description and can request their use during an iteration.

The harness then handles execution and returns the results.

### 5. Manage context and observations

I worked on the mechanism for preserving successive exchanges between the model, the user, and the tools.

The results of tool calls are integrated into the history to be exploited in subsequent iterations.

This context management is essential: an agent must be able to use previously obtained information to continue its work.

### 6. Govern iterations and stopping conditions

An agentic loop must have mechanisms to control its execution.

Flint integrates a limit on the number of iterations.

When this limit is reached, the code provides for a final solicitation of the model without the possibility of calling new tools, in order to obtain a final response.

An error path is also provided when this finalization fails.

These mechanisms prevent an agent from indefinitely pursuing a succession of calls.

### 7. Explore MCP integration

The Flint documentation also describes support for the **Model Context Protocol (MCP)**.

This approach aims to facilitate the agent's access to tools and services exposed through a standardized protocol.

It enables considering an extensible architecture, in which the agent's capabilities can evolve independently of the model used.

### 8. Develop Flint with Codex and GitHub

I used OpenAI Codex to assist me in developing Flint.

I drove the application's evolution by defining expected features, guiding architectural choices, and working on the various components of the harness.

The project fits within my development method based on the systematic use of a GitHub repository.

This organization allows preserving code history, tracking evolution, and controlling modifications introduced during iterations with Codex.

## Lessons Learned

### 1. An AI agent is an orchestration system, not just a language model

The model proposes actions, but it is the harness that organizes interactions, executes tools, retains observations, and controls processing continuation.

### 2. Building your own harness allows understanding agent frameworks

By directly implementing the agent loop, I was able to explore mechanisms that higher-level frameworks often make less visible.

This understanding facilitates analysis and use of other orchestration solutions.

### 3. Separation between model and orchestrator is fundamental

A common interface allows evolving the model provider without rebuilding the entire agent architecture.

### 4. Tools give the agent an ability to act

*Tool calling* transforms a generative model into a component capable of requesting operations and using their results to continue a task.

### 5. An agentic loop must be controlled

Limiting iterations, defining stop conditions, and managing errors are essential to control an agent's operation.

### 6. GitHub is indispensable for AI-assisted development

Versioning allows tracking changes proposed by Codex, maintaining control over the architecture, and reverting problematic evolutions.

### 7. Codex accelerates development, but design remains decisive

The effectiveness of AI-assisted development relies on the ability to define component responsibilities, guide technical choices, and understand the functioning of the resulting system.

**Flint constitutes a structuring step in my artificial intelligence journey: by developing my own harness, I moved from using AI agents to understanding and implementing their fundamental execution and orchestration mechanisms.**
