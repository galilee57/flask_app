# Designing a native multi-agent orchestration platform in Rust with Codex

## Context

After my first experiments with AI agents and the development of **FLINT**, I wanted to go further in designing agent systems.

My goal was to have a native application that not only allowed me to converse with different language models but also to organize their collaboration within configurable processes.

I undertook the development of this platform in **Rust**, with assistance from **OpenAI Codex**, using **egui/eframe** to build the graphical interface.

I wanted to be able to define agent roles, their instructions, available tools, documents to exploit, and information exchanged between different steps.

The application was also intended to allow tracking process execution, identifying errors, and maintaining visibility on the models involved.

I chose to apply this platform to a personal use case related to health data, in order to experiment with document organization, synthesis production, and control of information transmitted to models.

## Objectives

- Develop a native desktop application in Rust.
- Integrate local models via Ollama and remote models via the OpenAI API.
- Design a configurable multi-agent orchestration engine.
- Allow defining agents, their roles, skills, and tools.
- Build processes composed of several interdependent steps.
- Propose a visual configuration and supervision interface.
- Manage conversations, documents, and agent memories.
- Ensure traceability of executions and produced reports.
- Control the context sources accessible to different agents.
- Experiment with these features on a document-related health use case.

## Approach and implementation

### 1. Develop a native application in Rust

I chose Rust to build a desktop application and deepen my skills in a language different from Python.

Development relies on **egui/eframe**, which allows creating a native graphical interface.

The application offers a conversation environment with language models and retains exchanges as well as associated settings for each thread.

This first foundation constitutes the starting point of the orchestration platform.

### 2. Design an architecture independent of model providers

I organized the platform around a separation between the orchestration engine and model adapters.

The application supports two execution modes:

- **Ollama**, to use locally executed models.
- **The OpenAI API**, to access remotely hosted models.

The provider and model can be selected at the level of each agent.

This architecture allows associating multiple models within the same process, without imposing a single provider on all steps.

The OpenAI API key is stored in **macOS Keychain**, rather than directly in the application's standard settings.

### 3. Build a multi-agent orchestration engine

I developed a platform enabling the definition of processes composed of multiple agents and steps.

Each agent has a configuration specifying, among other things:

- Its role and instructions.
- Its skills.
- The tools it can access.
- The provider and model used.
- The available context elements.

Each step defines a mission and the information from previous steps that it must receive.

This organization allows distributing different responsibilities between agents, for example document analysis, information verification, and preparation of a synthesis.

Dependencies between steps and stopping conditions are part of the process configuration.

### 4. Create a visual process builder

To make orchestration more accessible, I enriched the application with a process builder based on forms and a visual representation of steps.

The goal is to be able to design and modify a process without having to intervene directly in the engine's code.

The interface allows working on agents, their missions, and relationships between steps.

This feature constitutes an important element of the project: **transforming technical orchestration logic into a configuration environment usable from a graphical interface.**

### 5. Monitor executions

I integrated a dashboard to track the progress of processes.

It makes visible:

- Executed steps.
- Agents and models mobilized.
- Execution durations.
- Generated reports.
- Encountered errors.

This visibility facilitates analysis of system behavior and identification of difficulties during experiments.

It also allows understanding how information progresses from one step to another.

### 6. Manage documents and agent memory

The platform allows enriching agents' context from local documents and selected memories.

I worked on distinguishing between mission-specific information and that which can be reused in other processes.

A shared memory can be populated after a review and validation step.

This approach aims to prevent information produced by an agent from being automatically considered reliable and reused without control.

Document management and memory thus become integral components of the agent architecture.

### 7. Control flows between local and remote models

The joint use of Ollama and the OpenAI API raises an important question: what information can be transmitted to each provider?

I integrated this concern into the platform design by working on selecting the context sources accessible to agents.

The configuration allows reserving certain sources for local processes and regulating those used by agents calling a remote API.

This separation constitutes an important design mechanism.

However, it does not exempt one from verifying network flows and the data actually transmitted to establish confidentiality guarantees.

### 8. Apply the platform to health data

I chose a personal use case related to health data to implement the developed features.

This field requires particular attention to document organization, information provenance, and their confidentiality.

My work covers three complementary dimensions.

**The documentary dimension:** organizing documents and selecting information useful for each mission.

**The agent dimension:** defining agents, their responsibilities, and the steps necessary to produce a synthesis.

**The data flow dimension:** choosing local or remote processes based on the mobilized information.

The goal is to produce documentary syntheses whose sources can be examined, not to develop a medical diagnostic device.

This use case allows me to confront the platform's capabilities with concrete constraints of personal data management.

### 9. Pilot development with OpenAI Codex

I designed and evolved the platform with the assistance of Codex.

My role consists of defining needs, specifying features, guiding architectural choices, and examining development results.

I worked through successive iterations to enrich the application:

- Conversation interface.
- Provider adapters.
- Agent configuration.
- Process engine.
- Visual builder.
- Document management and memory.
- Execution supervision.
- Error management.

This approach led me to precisely define expected behaviors, component interactions, and failure scenarios.

Tests accompany engine evolution and exchanges with suppliers.

The project also fits into my development method based on code versioning with Git and GitHub.

## Lessons Learned

### 1. Multi-agent orchestration is primarily an architecture problem

The difficulty does not lie solely in model calls, but in defining responsibilities, dependencies, and information exchanged between agents.

### 2. A graphical interface makes orchestration more accessible

The visual builder enables transitioning from a technical configuration to an understandable and modifiable process design approach.

### 3. Supervision is essential to understand agents

Dashboards, reports, and visibility into errors allow analyzing system behavior rather than considering only its final response.

### 4. Memory requires governance

Information produced by a model should not automatically become reusable knowledge.

The review and validation step for the shared memory constitutes a response to this issue.

### 5. Confidentiality depends on the complete architecture

Combining local and remote models requires reflection on context sources, transmission rules, and controls actually applied.

### 6. Rust enables exploring another approach to application development

This project allowed me to deepen the design of native applications and expand my experience beyond Python and web technologies.

**This project represents a new step in my exploration of agentic artificial intelligence. After developing a harness to understand how an agent works, I designed with Codex a native platform in Rust to organize, configure, and supervise multi-agent processes, then confront them with a demanding documentary use case.**
